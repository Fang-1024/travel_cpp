## 二、V0 究竟要实现什么？

先定义最小功能需求。

本阶段目标调用方式

```
mini_log::Logger app("app");

app.debug("Starting...");
app.info("Application started");
app.warn("Configuration missing");
app.error("Cannot open file");
```

预期输出示例

```
[DEBUG] [app] Starting...
[INFO]  [app] Application started
[WARN]  [app] Configuration missing
[ERROR] [app] Cannot open file
```

此处表示每条日志的文本格式。DEBUG/INFO 输出到 stdout，WARN/ERROR 输出到 stderr；两个输出流合并显示时，跨流顺序不作保证。

本阶段必须满足四个要求：

1. 可以创建多个相互独立的 Logger 对象，每个对象具有自己的名称。
2. 可以输出四种等级的日志，并包含 Logger 名称。
3. 用户通过公开成员函数写日志，不能随意访问或修改内部成员。
4. `log.h` 负责声明，`log.cpp` 负责实现，作为 CMake 中独立的 `lib_log` 库参与编译。

本阶段暂时不实现时间戳、等级过滤、文件日志、宏、模板、线程安全或继承。日志等级虽然不同，但全部允许输出。

判断 V0 是否真正完成的标准，不只是程序能够打印日志，而是你能够独立解释：Logger 为什么是一个类、对象保存了什么、成员函数属于谁，以及从 `main.cpp` 到 `log.cpp` 的调用关系。

# 三、先学原理：C++ 类到底是什么？

## 3.1 从普通函数开始思考

假设我们完全不知道什么是 `class`。

最简单的日志函数可能是：

```
#include <iostream>
#include <string>

void print_log(const std::string& message)
{
    std::cout << message << '\n';
}
```

调用：

```
print_log("Hello Logger");
```

这个函数可以工作，但还不能很好地表达一个“日志记录器”的概念。

假设程序中有两个模块：

```
Application
Network
```

我们希望：

```
[INFO] [Application] Started
[INFO] [Network] Connected
```

如果继续使用普通函数，就需要每次传入名称：

```
print_log("Application", "Started");
print_log("Network", "Connected");
```

问题是：既然某个模块的日志名称通常是固定的，为什么每次调用都需要重复传入？

这自然引出一个想法：

> 能不能创建一个日志记录器，让它记住自己的名称？

这就是本项目引入类的直接原因。

## 3.2 类是用户定义的类型

C++ 原本提供很多类型：

```
int age = 20;
double price = 9.9;
std::string name = "Alice";
```

我们还可以定义自己的类型：

```
class Logger
{
    // ...
};
```

以后就可以创建：

```
Logger app_logger;
Logger network_logger;
```

你应当建立一个非常重要的认识：

`Logger` 是类型；`app_logger` 和 `network_logger` 是该类型的两个对象。

可以这样理解：

同一个类创建多个对象，每个对象拥有独立的非静态成员变量。

`Logger` 描述对象应该具有哪些数据、可以执行哪些操作；真正创建对象后，程序才有了具体的日志记录器。

## 3.3 成员变量：对象拥有的数据

先看一个最简单的类：

```
class Logger
{
private:
    std::string name_;
};
```

这里：

```
std::string name_;
```

叫作成员变量（Data Member）。

这个变量表示日志记录器的名称。

例如，两个对象在概念上可以分别保存：

```
app_logger:
    name_ = "app"

network_logger:
    name_ = "network"
```

需要注意的是：普通非静态成员变量属于每一个对象，各对象拥有独立的成员值。

这和定义一个全局变量：

```
std::string logger_name;
```

有本质区别。

全局变量不是某个特定 Logger 对象的一部分。

思考题 1： 假设一个程序中有 100 个 Logger 对象，理论上可以存在多少个不同的 `name_` 值？

## 3.4 成员函数：对象能够执行的行为

继续扩展：

```
class Logger
{
public:
    void info(const std::string& message);

private:
    std::string name_;
};
```

这时有了：

- 数据：`name_`
- 行为：`info()`

在外部：

```
logger.info("Hello");
```

这里的 `.` 表示通过对象访问其成员。

而在实现文件中：

```
void Logger::info(const std::string& message)
{
    // ...
}
```

`Logger::info` 则表明：这个函数是 `Logger` 类的成员函数。

这两个符号的区别值得记住：

| 符号   | 常见用途       | 示例                 |
| ---- | ---------- | ------------------ |
| `.`  | 通过对象访问成员   | `logger.info()`    |
| `::` | 作用域解析      | `Logger::info()`   |
| `::` | 访问命名空间内的名字 | `mini_log::Logger` |

补充一个容易忽略的知识点：成员函数调用时，C++ 知道当前操作的是哪个对象。成员函数内部可以直接访问该对象的 `name_`。以后学到 `this` 指针时，你会更深入地理解这一机制。

## 3.5 public / private：为什么需要封装？

现在思考：

```
class Logger
{
public:
    std::string name_;
};
```

外部可以直接写：

```
logger.name_ = "anything";
```

如果我们希望 Logger 自己管理名称，就不应该允许外部随意操作其内部数据。

因此更合理的是：

```
class Logger
{
public:
    void info(const std::string& message);

private:
    std::string name_;
};
```

`public` 表示公开接口，`private` 表示只有类成员和友元等获得权限的代码才能访问的内部部分。

这个设计体现了两件事情：

数据隐藏（Data Hiding）： 不允许外部依赖内部数据的具体组织方式。

封装（Encapsulation）： 把相关状态和操作状态的行为组织到同一个类型中，通过明确的接口使用它。

因此，外部应该使用：

```
logger.info("Hello");
```

而不是直接操作 Logger 内部如何输出、如何保存名称。

思考题 2： 如果 `name_` 是私有的，为什么 `Logger::info()` 仍然能够读取它？

# 四、构造函数：对象的名称从哪里来？

我们希望这样创建对象：

```
Logger logger("app");
```

但是：

```
"app"
```

如何进入对象内部的 `name_` 呢？

答案是构造函数（Constructor）。

声明：

```
class Logger
{
public:
    explicit Logger(const std::string& name);

private:
    std::string name_;
};
```

实现：

```
Logger::Logger(const std::string& name)
    : name_(name)
{
}
```

这是本阶段最值得反复理解的语法之一。

## 4.1 构造函数有什么特点？

它的名称与类名相同：

```
Logger::Logger(...)
```

它没有返回类型，连 `void` 也不需要。

当代码执行：

```
Logger logger("app");
```

时，对象构造过程中会执行构造函数。

## 4.2 成员初始化列表是什么？

关注：

```
: name_(name)
```

左侧的 `name_` 是成员变量，括号里的 `name` 是构造函数参数。

其含义是：

> 使用构造函数接收到的 `name`，初始化当前对象的 `name_` 成员。

成员初始化发生在构造函数函数体执行前。

```
Logger::Logger(const std::string& name)
    : name_(name)
{
    // 进入这里时 name_ 已经完成初始化
}
```

这里不是先默认构造 `name_` 再对它赋值，而是直接用参数初始化该成员。

对于 C++ 类，正确理解成员初始化列表非常重要。以后遇到引用成员、`const` 成员以及资源管理类时，它会更加关键。

这里还有两个词需要先认识：

`const std::string&` 表示以常量引用方式接收字符串参数；`explicit` 用于避免某些不期望的隐式转换。它们将在 V1 中系统展开，V0 只需知道接口为什么这样写，不必一次掌握所有细节。

思考题 3： 为什么构造函数通常要在创建对象时执行，而不是要求用户先创建一个未正确初始化的对象，再手动调用普通初始化函数？

# 五、enum class：如何表达日志等级？

我们需要四个等级：

```
Debug
Info
Warn
Error
```

一个简单做法是使用整数：

```
void log(int level, const std::string& message);
```

但这带来问题：

```
log(7, "Hello");
```

这里的 `7` 是什么意思？

所以使用枚举类型：

```
enum class Level
{
    Debug,
    Info,
    Warn,
    Error
};
```

调用：

```
Level::Info
```

就非常清晰。

`enum class` 是强类型枚举，不会像普通整数那样随意参与隐式转换。

本阶段只是用它表达日志种类：

```
log(Level::Info, message);
```

暂时不比较等级大小。`min_level_` 和日志过滤留到 V1。

# 六、V0 的 Logger 类应该如何设计？

现在终于可以把这些概念组合起来。

我推荐的设计是：

```
mini_log
│
├── Level
│   ├── Debug
│   ├── Info
│   ├── Warn
│   └── Error
│
└── Logger
    │
    ├── public
    │   ├── Logger()
    │   ├── debug()
    │   ├── info()
    │   ├── warn()
    │   └── error()
    │
    └── private
        ├── name_
        └── log()
```

这里有个关键问题：

为什么还需要一个私有的 `log()` 函数？

因为四种日志方法最终都要进行非常类似的输出操作。

例如：

```
void Logger::info(const std::string& message)
{
    log(Level::Info, message);
}
```

```
void Logger::error(const std::string& message)
{
    log(Level::Error, message);
}
```

公开接口负责表达用户意图；内部 `log()` 负责统一处理输出。

这样避免复制四份几乎相同的代码。

调用关系为：

```
logger.info("Hello")
        |
        v
Logger::info()
        |
        v
Logger::log(Level::Info, "Hello")
        |
        v
std::cout
```

这种结构足够简单，也具有清晰的职责划分。

# 九、GoogleTest 测试设计

你的仓库已经有 GoogleTest，可以先在 `tests/test_demo.cpp` 增加 Logger 测试，暂时不用拆分独立测试文件。

## 测试一：Info 日志格式

希望测试：

```
logger.info("Hello");
```

是否产生：

```
[INFO] [app] Hello
```

可以用 `std::ostringstream` 临时接管 `std::cout` 的输出缓冲区。

```
#include <gtest/gtest.h>

#include <iostream>
#include <sstream>

#include <travel_cpp/log.h>

TEST(LoggerV0Test, InfoContainsNameAndMessage)
{
    std::ostringstream captured;

    std::streambuf* old_buffer =
        std::cout.rdbuf(captured.rdbuf());

    mini_log::Logger logger("app");
    logger.info("Hello");

    std::cout.rdbuf(old_buffer);

    EXPECT_EQ("[INFO] [app] Hello\n", captured.str());
}
```

这一小段测试代码涉及 `rdbuf()` 和流缓冲区，它不是 V0 重点。你暂时可以把它理解成“把输出临时转存到字符串里，以便检查”。

注意：这种直接替换 `std::cout` 缓冲区的办法适合当前单线程、简单测试。它会暂时改变全局输出流状态，必须及时恢复，并非以后并发测试的推荐方法。

# 十二、和 V1、V3 的衔接

当 V0 完成后，V1 会自然引出新的问题：

> 现在所有 Logger 都输出四种日志，但实际工程中有些模块只希望输出 Warn 和 Error，怎么办？

于是给 Logger 增加 `min_level_`，你就能学习更完整的构造函数、const 成员函数、对象状态修改及接口设计。

到了 V3，我们再解决：

```
logger.info("User=", name, ", id=", id);
```

这会涉及你提到的可变参数模板、参数包和折叠表达式。它们更适合在你已经熟悉普通成员函数和函数参数之后学习。

为了与教材配合，V0 可以优先参考《C++ 哈氏教程》第二版第 6.5 节（类初步）、第 7.1～7.2 节（跨文件编译、命名空间），以及《C++ Primer Plus》第 10 章（Objects and Classes）。深入的构造、析构与对象生命周期内容可以留在后续阶段。
