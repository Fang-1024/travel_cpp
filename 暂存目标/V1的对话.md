## 二、V1 的需求是什么？

先不谈语法，先谈工程问题。

假设你开发一个程序，其中有两个模块：

```
Application：主程序逻辑
Network：网络通信
```

你希望主程序只打印普通运行信息、警告与错误，而网络模块在调试时还能打印 Debug。

你当然可以在每次调用时做判断：

```
if (some_condition)
{
    logger.debug("Connecting...");
}
```

但这样的判断会散落在业务代码里。

更合适的做法是把“允许打印什么等级”作为 Logger 自己的配置。

我们希望：

```
mini_log::Logger app(
    "app",
    mini_log::Level::Info);

mini_log::Logger network(
    "network",
    mini_log::Level::Debug);
```

然后：

```
app.debug("Debug message");       // 不打印
app.info("Application started");  // 打印

network.debug("Connecting...");   // 打印
```

还希望程序运行过程中能够修改：

```
app.set_min_level(mini_log::Level::Warn);
```

之后：

```
app.info("Application running"); // 不打印
app.warn("Low disk space");      // 打印
```

这就是 V1 的核心工程需求。

## V1 的状态与行为模型

两个 Logger 对象属于相同的类，但拥有彼此独立的配置和输出行为。

V0 的重点是：

> 对象有自己的数据和函数。

V1 则进一步证明：

> 对象的内部状态能够决定它执行某个操作时的具体行为。

这是一条非常重要的面向对象编程主线。

# 四、核心知识一：对象状态（Object State）

## 4.1 为什么一个对象需要保存状态？

V0 中：

```
class Logger
{
private:
    std::string name_;
};
```

已经有一个状态变量。

现在 V1 要增加：

```
Level min_level_;
```

这个变量表示：

> 当前 Logger 允许输出的最低日志等级。

例如：

```
Logger logger("app", Level::Warn);
```

对应的状态可以理解为：

```
logger 对象
┌──────────────────────────┐
│ name_ = "app"            │
│ min_level_ = Level::Warn │
└──────────────────────────┘
```

当用户执行：

```
logger.info("Hello");
```

时，成员函数要读取 `min_level_`，决定这条日志是否应该打印。

因此，对象状态不只是被动保存信息，它会参与对象内部行为的决策。

## 4.2 成员变量与局部变量有什么区别？

请比较两段代码。

第一段：

```
void Logger::set_min_level(Level level)
{
    Level min_level = level;
}
```

第二段：

```
void Logger::set_min_level(Level level)
{
    min_level_ = level;
}
```

第一段定义的是一个普通局部变量：

```
Level min_level;
```

它只在本次函数调用的作用域内存在，函数执行结束后，局部变量的生命周期也结束。

第二段修改的是：

```
min_level_
```

即当前 Logger 对象的成员变量。

该成员的生命周期与所属 Logger 对象相联系，函数调用结束不会使它消失。

所以：

```
logger.set_min_level(Level::Warn);
logger.info("Hello");
```

第二次调用仍然能够读取前一次修改后的状态。

这是 成员变量与局部变量 的本质区别之一。

## 4.3 两个对象会互相影响吗？

假设：

```
Logger app("app", Level::Info);
Logger network("network", Level::Debug);
```

然后：

```
app.set_min_level(Level::Error);
```

被修改的是 `app` 对象的 `min_level_`，并不会修改 `network` 的成员变量。

```
修改前：
app       → Info
network   → Debug

修改后：
app       → Error
network   → Debug
```

这里的“独立状态”是指两个独立创建的对象分别拥有自己的非静态成员变量。后面讲到对象复制时，我们还会讨论复制之后的独立性。

# 五、核心知识二：构造函数与成员初始化列表

这一部分是 V1 的第一个重点。

## 5.1 从一个参数升级到两个参数

V0：

```
Logger::Logger(const std::string& name)
    : name_(name)
{
}
```

现在希望：

```
Logger logger("app", Level::Warn);
```

这意味着构造函数除了接收 `name`，还要接收 `min_level`。

可以修改成：

```
Logger::Logger(
    const std::string& name,
    Level min_level)
    : name_(name),
      min_level_(min_level)
{
}
```

现在讨论构造过程。

当执行：

```
Logger logger("app", Level::Warn);
```

时，程序需要完成以下操作：

开始构造 Logger 对象

初始化 `name_`

使用构造函数参数 name

初始化 `min_level_`

使用构造函数参数 min_level

执行构造函数体 `{}`

Logger 对象构造完成

这里省略了更底层的对象存储与构造细节，重点是：成员初始化先于构造函数体执行。

## 5.2 初始化与赋值有什么区别？

下面两种代码看起来很接近。

写法 A：

```
Logger::Logger(
    const std::string& name,
    Level min_level)
    : name_(name),
      min_level_(min_level)
{
}
```

写法 B：

```
Logger::Logger(
    const std::string& name,
    Level min_level)
{
    name_ = name;
    min_level_ = min_level;
}
```

对于当前的 `std::string` 和 `Level`，这两种写法在正常执行完成后，可以得到相同的成员值。

但底层过程不同。

| 对比           | 写法 A：初始化列表   | 写法 B：函数体赋值        |
| ------------ | ------------ | ----------------- |
| `name_`      | 用参数直接构造字符串成员 | 先默认构造字符串，再赋值      |
| `min_level_` | 直接初始化枚举成员    | 进入函数体前先默认初始化，随后赋值 |
| `const` 数据成员 | 可以在初始化列表中初始化 | 不能在函数体中重新赋值       |
| 引用数据成员       | 必须初始化绑定      | 不能先不绑定，之后赋值       |
| 日常推荐         | 优先使用         | 只在确实需要赋值时使用       |

尤其注意第二行。对于 `Level` 这样的枚举类型，如果没有成员默认初始化器，又没有在初始化列表中指定值，默认初始化并不会保证它获得有效的枚举值。

因此，即便构造函数体马上执行赋值，也没有必要先留下一个未明确初始化的状态。

在 V1 中，请优先使用成员初始化列表。

## 5.3 成员的初始化顺序由什么决定？

这是初学者非常容易忽略的问题。

假设头文件是：

```
class Logger
{
private:
    std::string name_;
    Level min_level_;
};
```

构造函数却写成：

```
Logger::Logger(
    const std::string& name,
    Level min_level)
    : min_level_(min_level),
      name_(name)
{
}
```

你会不会认为 `min_level_` 比 `name_` 先初始化？

实际上不是。

对于普通非静态成员，在这个类中，真正的初始化顺序是：

```
1. name_
2. min_level_
```

因为 C++ 按照成员在类中的声明顺序初始化，而不是按照成员初始化列表里的书写顺序。

所以建议把初始化列表也按声明顺序写：

```
: name_(name),
  min_level_(min_level)
```

这样代码更易理解，也避免编译器的成员初始化顺序警告。

这个规则在以后成员之间存在依赖时尤其重要。

# 六、核心知识三：默认参数（Default Argument）

## 6.1 为什么我们希望构造函数有默认参数？

V0 支持：

```
Logger logger("app");
```

现在 V1 引入最低日志等级，如果必须写：

```
Logger logger("app", Level::Debug);
```

那么所有原来使用 V0 的代码都需要修改。

但实际上，很多 Logger 默认允许所有等级输出就可以了。

因此可以声明：

```
explicit Logger(
    const std::string& name,
    Level min_level = Level::Debug);
```

现在有两种使用方式：

```
Logger a("app");
```

等价于在调用时使用默认值：

```
Logger a("app", Level::Debug);
```

也可以明确指定：

```
Logger b("network", Level::Warn);
```

注意，这不是定义了两个不同的构造函数。

我们仍然只有一个构造函数，只是第二个参数有默认实参。

## 6.2 默认参数应该写在哪里？

对于你的项目，应该写在头文件中的声明上：

```
// log.h
explicit Logger(
    const std::string& name,
    Level min_level = Level::Debug);
```

实现文件：

```
// log.cpp
Logger::Logger(
    const std::string& name,
    Level min_level)
    : name_(name),
      min_level_(min_level)
{
}
```

不要在类外定义中重复写 `= Level::Debug`。

因为调用者在编译自己的 `.cpp` 时，需要从可见的构造函数声明获知默认参数，而不是等链接到 `log.cpp` 时再决定。

这是理解“声明提供接口信息，定义提供实现”很好的例子。

# 七、核心知识四：`explicit` 与隐式类型转换

你在 V0 已经使用了：

```
explicit Logger(const std::string& name);
```

V1 可以把它真正理解透。

## 7.1 C++ 的隐式转换

你已经见过这样的代码：

```
double x = 10;
```

虽然 `10` 是整数，但 C++ 允许把它转换成 `double`。

对于类，某些构造函数也能充当类型转换的入口。

假设不使用 `explicit`：

```
class Logger
{
public:
    Logger(const std::string& name);
};
```

那么在适用的情况下：

```
std::string name = "app";

Logger logger = name;
```

可以通过构造函数把 `std::string` 转换成 Logger。

这里的：

```
Logger logger = name;
```

叫作复制初始化（Copy Initialization）。尽管名字含有“复制”，但此例涉及的是从 `std::string` 构造 `Logger`，并不意味着先复制一个现成的 Logger 对象。

## 7.2 加上 explicit 后

```
class Logger
{
public:
    explicit Logger(const std::string& name);
};
```

现在：

```
std::string name = "app";

Logger logger = name; // 不允许
```

但：

```
Logger logger(name); // 允许
```

或者：

```
Logger logger{name}; // 允许
```

都可以。

原因是：`explicit` 构造函数可以参与这些直接初始化形式，但不能用于普通的隐式转换式复制初始化。

## 7.3 为什么 Logger 适合 explicit？

设想一个函数：

```
void start(Logger logger);
```

如果构造函数允许隐式转换，那么某些调用可能在没有明确写出 Logger 的情况下，自动构造一个 Logger 对象。

这会使 API 行为不够直观。

Logger 是一个具有明确业务意义的对象，因此要求调用者显式创建它比较合理：

```
Logger logger("app");
```

这里需要补充一个细节：

V1 的构造函数虽然有两个参数，但第二个参数有默认值，因此它仍然可以只用一个实参调用，也仍然有必要考虑 `explicit`。

# 八、核心知识五：值传递、引用与 const 引用

这是整个 V1 最重要的知识之一。

目前构造函数同时使用了两种传参方式：

```
Logger(
    const std::string& name,
    Level min_level);
```

为什么：

```
name
```

使用：

```
const std::string&
```

而：

```
min_level
```

直接使用：

```
Level
```

呢？

## 8.1 值传递

先看：

```
void change(int x)
{
    x = 100;
}
```

调用：

```
int value = 10;

change(value);
```

执行结束后：

```
value
```

仍然为 `10`。

因为参数 `x` 是按照值传递的，函数获得的是自己的参数对象，而不是直接修改调用者的 `value`。

对于：

```
void set_min_level(Level level);
```

同样如此。

`Level` 只是一个简单枚举值，直接按值传递清晰、开销很小。

## 8.2 引用传递

再看：

```
void change(int& x)
{
    x = 100;
}
```

调用：

```
int value = 10;

change(value);
```

执行之后：

```
value
```

变成了 `100`。

因为 `x` 是 `value` 的引用。

可以把引用理解成已有对象的另一个访问名称，而不是简单地认为它必然占据某个固定大小的指针存储空间。

引用在底层如何表示属于实现细节。

## 8.3 const 引用

如果函数只需要读取参数，不希望修改调用者的对象：

```
void print(const std::string& text)
{
    std::cout << text;
}
```

此时：

```
text = "changed";
```

不允许，因为：

```
const std::string&
```

意味着不能通过这个引用修改其所引用的字符串。

这很适合 Logger：

```
void Logger::info(
    const std::string& message) const;
```

日志函数主要读取消息内容，并不需要修改传进来的字符串。

## 8.4 为什么不把 string 直接按值传递？

比较：

```
void print(std::string text);
```

和：

```
void print(const std::string& text);
```

如果传入一个已有的较长字符串：

```
std::string message = "...";

print(message);
```

第一种写法需要构造一个参数字符串副本。

第二种写法绑定到原来的字符串，不需要因为参数传递而复制整个字符串。

因此，对于只读的 `std::string` 参数，`const std::string&` 是很常见的设计。

但请不要把它理解成绝对规则。

对于构造函数这样需要保存参数内容的场景：

```
Logger(const std::string& name)
    : name_(name)
{
}
```

虽然参数通过引用传递，`name_` 仍然需要复制字符串内容。

以后学习移动语义时，我们还会比较：

```
Logger(std::string name)
    : name_(std::move(name))
{
}
```

为什么在某些场景下也很合适。

目前不必提前引入 `std::move`。

## 8.5 const 引用是否意味着 Logger 保存的是引用？

不是。

这是一个非常值得理解的细节。

你的成员声明：

```
std::string name_;
```

是一个真正的字符串对象。

而不是：

```
const std::string& name_;
```

因此，假设：

```
std::string name = "app";

Logger logger(name);

name = "network";
```

Logger 内部保存的名称仍然是构造时复制得到的 `"app"`。

可以理解成：

```
外部变量 name       Logger 内部 name_
┌─────────────┐     ┌──────────────┐
│ "network"   │     │ "app"        │
└─────────────┘     └──────────────┘
```

这避免了 Logger 依赖外部字符串的生命周期。

同理：

```
Logger logger("app");
```

也是有效的。

这里的字符串字面量可以用于构造临时 `std::string` 并绑定到构造函数的 `const std::string&` 参数，而 `name_` 在构造过程中复制自己的内容。

构造完成后，Logger 不依赖那个临时字符串继续存在。

这恰好引出了一个现代 C++ 的基本设计原则：

> 对象保存长期使用的数据时，应该明确这些数据是自己拥有的，还是借用自外部对象。

你的 `std::string name_` 采用的是自己拥有字符串值的方式，对于当前 Logger 非常合理。

# 九、核心知识六：const 成员函数

你 V0 的代码已经使用了：

```
void info(const std::string& message) const;
```

但 V1 需要真正理解最后一个 `const`。

## 9.1 两个 const 的区别

观察：

```
void info(const std::string& message) const;
```

这里有两个 `const`。

第一个：

```
const std::string& message
```

限制的是函数如何通过 `message` 引用访问参数。

第二个：

```
... ) const
```

限制的是成员函数如何修改当前 Logger 对象。

二者是不同的约束。

## 9.2 const 成员函数不能修改普通成员状态

例如：

```
Level Logger::min_level() const
{
    return min_level_;
}
```

合法，因为只是读取。

但是：

```
Level Logger::min_level() const
{
    min_level_ = Level::Error; // 编译错误
    return min_level_;
}
```

不合法，因为普通非静态成员函数的末尾 `const` 约束了对当前对象的修改。

可以粗略理解为：成员函数隐含的 `this` 指针在这里具有类似下面的类型：

```
const Logger* const this
```

这是帮助理解的概念性写法，不是你可以自己声明的普通参数。

它表示不能通过当前对象的 `this` 随意修改非 `mutable` 数据成员。

## 9.3 修改对象状态的成员函数不能是 const

例如：

```
void Logger::set_min_level(Level level)
{
    min_level_ = level;
}
```

这里没有末尾的 `const`。

因为函数确实修改对象的成员。

对比：

```
Level min_level() const;       // 读取
void set_min_level(Level);     // 修改
```

这种对不同操作进行区分的做法，就是 C++ 中 const correctness（const 正确性）的一部分。

## 9.4 为什么 info() 可以是 const？

你可能会发现：

```
void Logger::info(
    const std::string& message) const
{
    log(Level::Info, message);
}
```

`info()` 虽然有输出副作用，但它没有修改 Logger 的 `name_`、`min_level_`。

因此可以是 `const`。

这里应当区分：

- 不修改 Logger 对象自身的普通成员状态。
- 不产生任何外部可观察的副作用。

这两者并不是一回事。

向 `std::cout` 输出内容是一种副作用，但并不必然违反 Logger 成员函数的 `const` 约束。

## 9.5 const 对象能调用什么函数？

例如：

```
const Logger logger("app", Level::Info);
```

这个 Logger 对象被声明为 `const`。

因此：

```
logger.info("Hello"); // 允许
```

因为 `info()` 是 `const` 成员函数。

但是：

```
logger.set_min_level(Level::Warn); // 编译错误
```

因为 setter 是非 `const` 成员函数。

这就是为什么对于只读取对象状态的方法，尽可能合理地声明为 `const` 很重要。

## 9.6 const 不等于线程安全

这点暂时只需要有概念。

即使：

```
void info(...) const;
```

也不能由此推断多个线程同时调用 `info()` 就一定安全。

因为线程安全还涉及共享资源、同步、生命周期等问题。

这些要到 V4 再系统学习。

# 十、核心知识七：Getter、Setter 与封装

我们已经知道 `min_level_` 是私有成员：

```
private:
    Level min_level_;
```

如果外部想修改它，怎么办？

例如：

```
logger.min_level_ = Level::Warn;
```

这会产生访问控制错误。

因此可以通过公开的成员函数实现读取和修改。

## 10.1 Setter：修改状态

在 `log.h` 中声明：

```
void set_min_level(Level level);
```

在 `log.cpp` 中定义：

```
void Logger::set_min_level(Level level)
{
    min_level_ = level;
}
```

之后外部可以：

```
logger.set_min_level(Level::Warn);
```

这会修改当前 Logger 对象的状态。

注意：

```
min_level_ = level;
```

左边是成员变量，右边是函数参数。

如果采用现代 C++ 的惯用命名方式，成员变量带有尾部下划线，正好能够直观地区分两者。

## 10.2 Getter：读取状态

定义：

```
Level min_level() const;
```

对应实现：

```
Level Logger::min_level() const
{
    return min_level_;
}
```

然后：

```
Level current = logger.min_level();
```

这里直接按值返回 `Level` 是合理的，因为它是一个很小的枚举值，没有必要返回引用。

Getter 使用：

```
const
```

因为读取最低日志等级不需要修改 Logger。

## 10.3 为什么不直接把 min_level\_ 设置为 public？

假设：

```
class Logger
{
public:
    Level min_level_;
};
```

外部确实可以直接：

```
logger.min_level_ = Level::Warn;
```

对于极简单的纯数据类型，公开数据成员并不一定错误。

但 Logger 不只是数据结构，它还负责输出日志、执行过滤等行为。

今天设置最低等级只是简单赋值，未来可能还需要：

- 检查配置是否有效。
- 通知其他内部组件。
- 更新某个缓存的状态。
- 维护多个成员之间的一致性。

如果从一开始就把 `min_level_` 暴露出来，未来改变内部实现就更困难。

通过 setter，可以为这些变化保留明确的接口边界。

不过这里也要避免另一个误区：

> 不是每个 private 成员都必须同时拥有 Getter 和 Setter。

例如当前的：

```
std::string name_;
```

如果我们暂时不希望 Logger 创建后还能更名，就没有必要提供：

```
void set_name(...);
```

封装的核心并不是机械地给每个成员生成 Getter/Setter，而是只公开真正需要的操作。

# 十一、核心知识八：enum class 的比较与日志过滤

这一部分是 V1 的主要业务逻辑。

我们已经有：

```
enum class Level
{
    Debug = 0,
    Info = 1,
    Warn = 2,
    Error = 3
};
```

可以认为：

```
Debug  <  Info  <  Warn  <  Error
  0        1        2        3
```

现在约定：

> 当前日志等级大于或等于 Logger 最低允许等级时，才打印这条日志。

数学上：

\\[ \operatorname{shouldLog}(L,M)=(L\ge M) \\]

其中：

- \\(L\\)：当前日志等级。
- \\(M\\)：最低允许等级。

## 11.1 用一个交互表理解过滤规则

模拟 Logger 的最低输出等级

Debug（输出全部日志）

Info（不输出 Debug）

Warn（只输出 Warn、Error）

Error（只输出 Error）

当前过滤结果

Debug

过滤

Info

允许输出

Warn

允许输出

Error

允许输出

判断表达式：`current_level >= min_level_`。这里的最低等级是包含边界的。

重点观察：如果最低等级是 `Warn`，那么 Warn 本身必须输出。

这是上次代码审查中发现过的边界问题，因此建议你这次特别重视 `>=` 和 `>` 的区别。

## 11.2 应该如何实现 should_log()？

在 `Logger` 内增加私有成员函数：

```
bool should_log(Level current_level) const;
```

我建议它作为普通的私有非静态成员函数，而不是静态成员函数。

为什么？

因为它需要读取当前 Logger 对象的：

```
min_level_
```

因此它的行为依赖对象状态。

对应实现非常简单：

```
bool Logger::should_log(Level current_level) const
{
    return current_level >= min_level_;
}
```

这里有一个值得认识的知识点：

`enum class` 不允许像普通整数那样随意进行隐式整数转换，但同一个枚举类型的值可以直接进行关系比较。

因此：

```
current_level >= min_level_
```

是合法的。

你不必先写：

```
static_cast<int>(current_level) >=
static_cast<int>(min_level_)
```

两种方式都能表达当前意图，但直接比较 `Level` 更简单，而且不依赖额外的类型转换。

## 11.3 为什么 should_log() 要放在 private？

因为它是 Logger 的内部决策细节。

用户希望表达的是：

```
logger.info("Hello");
```

而不应该要求用户先写：

```
if (logger.should_log(Level::Info))
{
    logger.info("Hello");
}
```

如果这样设计，过滤的责任就被推给了外部调用者。

Logger 自己知道最低允许等级，因此应该自己负责判断。

这恰好体现了 V0 学到的封装思想。

## 11.4 为什么过滤应该放在 log() 开头？

你的 V0 代码中：

```
void Logger::log(
    Level current_level,
    const std::string& message) const
{
    std::ostream& output = /* ... */;

    output << " [" << name_ << "] "
           << message
           << '\n';

    output.flush();
}
```

V1 应该在函数开始处加入：

```
if (!should_log(current_level))
{
    return;
}
```

调用流程变成：

```
logger.info("Hello")
        │
        ▼
Logger::info()
        │
        ▼
Logger::log(Level::Info, "Hello")
        │
        ▼
should_log(Level::Info)
        │
        ├── false ──→ return，结束
        │
        └── true
              │
              ▼
         选择输出流
              │
              ▼
            输出
```

这叫作提前返回（Early Return）。

对于这里的逻辑，比把整个输出代码包裹在一个很大的 `if` 中更直观。

还有一个性能方面的限制需要明确：

如果调用：

```
logger.debug(
    "result=" + std::to_string(expensive_calculation()));
```

即便 Debug 被 Logger 过滤，`expensive_calculation()` 也已经在调用成员函数之前执行了。

因此，V1 能够避免不必要的日志输出，但不能保证避免所有参数构造或格式化开销。

这将成为后续模板接口与编译期过滤等优化的研究主题。

# 十二、核心知识九：对象生命周期、复制与 Rule of Zero

前面我们重点讨论了构造函数，但对象还有生命周期和复制的问题。

## 12.1 对象从何时开始，到何时结束？

例如：

```
void run()
{
    Logger logger("app");

    logger.info("Started");
}
```

`logger` 是一个具有自动存储期的局部对象。

程序执行到它的定义处时，对象被构造。

离开 `run()` 的作用域时，它被销毁。

概念上：

```
进入 run()
     ↓
构造 logger
     ↓
调用 info()
     ↓
离开作用域
     ↓
销毁 logger
```

Logger 有：

```
std::string name_;
Level min_level_;
```

当 Logger 被销毁时，其 `std::string` 成员也会自动被销毁。

因此我们现在不需要手写：

```
~Logger();
```

## 12.2 为什么不需要自己定义析构函数？

因为 Logger 目前没有手动管理的动态资源。

它的 `std::string` 成员能够自己管理所拥有的字符串资源。

这对应现代 C++ 的 Rule of Zero（零规则）：

> 如果一个类不需要自己管理某种底层资源的特殊生命周期行为，就尽量让编译器自动生成特殊成员函数。

对于当前 Logger，这是非常合适的。

以后 FileSink 持有文件、Logger 持有互斥锁或者后台线程时，我们再分析资源管理和特殊成员函数的需求。

## 12.3 现在的 Logger 可以复制吗？

考虑：

```
Logger app("app", Level::Info);

Logger another = app;
```

对于 V1 计划中的 Logger：

```
std::string name_;
Level min_level_;
```

编译器通常会自动生成可用的拷贝构造函数。

所以这段代码可以工作。

复制之后：

```
app
  name_ = "app"
  min_level_ = Info

another
  name_ = "app"
  min_level_ = Info
```

两者初始成员值相同。

但它们仍然是两个不同的对象。

例如：

```
another.set_min_level(Level::Warn);
```

并不会修改：

```
app
```

的最低等级。

这就回答了一个很重要的问题：

复制对象，不等于让两个对象成为同一个对象。

## 12.4 拷贝构造与拷贝赋值

这两个概念容易混淆。

```
Logger app("app", Level::Info);

Logger another = app;
```

这里 `another` 原本不存在，现在使用 `app` 初始化一个新对象。

这涉及拷贝构造。

而：

```
Logger app("app", Level::Info);
Logger another("network", Level::Warn);

another = app;
```

这里 `another` 已经存在，只是把 `app` 的成员状态赋值给它。

这涉及拷贝赋值。

| 操作              | 对象是否原本已存在 | 特殊成员函数 |
| --------------- | --------- | ------ |
| `Logger b = a;` | `b` 尚未构造  | 拷贝构造   |
| `b = a;`        | `b` 已经存在  | 拷贝赋值   |

当前版本无需手动实现这两个函数。

但是到了 V4，当 Logger 增加 `std::mutex` 之后，复制语义就会产生新问题。

因此，V1 的目的只是建立正确概念，为后面学习 `= delete`、Rule of Five 做准备。

# 十三、现在才开始设计 V1 的代码

前面的理论可以汇总成一个很小的升级。

你当前的 V0：

```
Logger
├── name_
├── debug()
├── info()
├── warn()
├── error()
└── log()
```

V1 只需要增加：

```
Logger
├── name_
├── min_level_          新增
├── Logger(name, level) 修改
├── set_min_level()     新增
├── min_level()         新增
├── debug()
├── info()
├── warn()
├── error()
├── should_log()        新增
└── log()               修改
```

请注意：这次不需要引入任何新的类。

没有必要增加：

```
class LoggerConfig;
```

也没有必要创建：

```
class LogManager;
```

这些都是后续工程需求真正出现时才考虑的设计。

## 13.1 推荐的头文件目标结构

这份代码作为 V1 的接口设计参考：

```
#pragma once

#include <string>

namespace mini_log
{

enum class Level
{
    Debug = 0,
    Info = 1,
    Warn = 2,
    Error = 3
};

class Logger
{
public:
    // 构造函数。
    explicit Logger(
        const std::string& name,
        Level min_level = Level::Debug);

    // 修改和读取最低日志等级。
    void set_min_level(Level level);
    Level min_level() const;

    // 日志接口。
    void debug(const std::string& message) const;
    void info(const std::string& message) const;
    void warn(const std::string& message) const;
    void error(const std::string& message) const;

private:
    // 内部日志实现。
    void log(Level current_level,
             const std::string& message) const;

    // 判断日志是否允许输出。
    bool should_log(Level current_level) const;

    // 对象状态。
    std::string name_;
    Level min_level_;
};

} // namespace mini_log
```

这里有几个设计约定。

第一，Getter 采用：

```
Level min_level() const;
```

而不是：

```
Level get_min_level() const;
```

两种命名都可以。这里选择前者是为了接口简洁，并且你的成员变量叫作 `min_level_`，不会产生名称冲突。

第二，Logger 的所有普通日志输出接口仍然保持 `const`。

第三，构造函数同时支持一个或两个实参。

第四，真正的过滤逻辑保留在私有成员函数中。

# 十四、亲手升级 V1：推荐五个实现阶段

为了避免从完整参考代码开始机械复制，我建议按照以下顺序动手。

## 阶段 1：给 Logger 增加最低日志等级

涉及文件：`log.h`、`log.cpp`

目标： 让每个 Logger 在创建时拥有独立的 `min_level_`。

你需要完成：

```
Level min_level_;
```

修改构造函数声明：

```
explicit Logger(
    const std::string& name,
    Level min_level = Level::Debug);
```

并修改成员初始化列表。

实现提示：

```
Logger::Logger(
    const std::string& name,
    Level min_level)
    : name_(name),
      min_level_(min_level)
{
}
```

验收重点是理解：

- 默认参数来自何处。
- 成员初始化列表在何时执行。
- 两个 Logger 是否分别拥有自己的 `min_level_`。

## 阶段 2：实现 Getter 与 Setter

涉及文件：`log.h`、`log.cpp`

目标： 外部能够修改和读取 Logger 的最低等级。

声明：

```
void set_min_level(Level level);
Level min_level() const;
```

先不要复制我的实现，尝试自己写出对应的两个成员函数。

完成后应该能够调用：

```
logger.set_min_level(Level::Warn);

Level level = logger.min_level();
```

思考：为什么 setter 不能是 `const`，而 getter 应该是 `const`？

## 阶段 3：实现 should_log()

涉及文件：`log.h`、`log.cpp`

目标： 让 Logger 自己判断当前日志等级是否允许输出。

声明：

```
bool should_log(Level current_level) const;
```

自己编写函数体，只使用：

```
current_level
min_level_
>=
```

即可。

这里不需要模板、容器或其他复杂结构。

## 阶段 4：在 log() 中完成过滤

涉及文件：`src/log.cpp`

你当前的 `log()` 已经实现了终端输出。

不要重写整个函数，只在开头增加过滤判断：

```
if (!should_log(current_level))
{
    return;
}
```

剩下的输出逻辑保持 V0 的实现即可。

特别强调：V1 的重点是日志过滤，不需要在此时重新添加时间戳。

你当前 V0 没有在文本中显示 `[INFO]` 这样的等级标签，只根据等级选择 `stdout/stderr`。等级标签可以作为独立的小型格式完善任务，不必与 V1 的状态管理混在一起。

## 阶段 5：使用不同的 Logger 对象

涉及文件：`main.cpp`

现在可以把主程序改成拥有两个 Logger：

```
mini_log::Logger app(
    "app",
    mini_log::Level::Info);

mini_log::Logger network(
    "network",
    mini_log::Level::Debug);
```

然后尝试：

```
app.info("Application started");

```

再修改：

```
app.set_min_level(mini_log::Level::Warn);
```

此后 `app.info()` 应当被过滤，而 `network.debug()` 仍然允许输出。

这能够很直观地观察到 V1 的最大变化：每个对象有独立的配置，而配置会影响行为。

# 十五、哪些常见错误应该提前避免？

这部分不是单元测试，而是实际编写 C++ 类时应当理解的语言错误。

| 常见问题                          | 原因                    | 正确思路                    |
| ----------------------------- | --------------------- | ----------------------- |
| 只声明 `min_level_`，没有初始化        | 枚举成员可能没有确定的初始值        | 在初始化列表中初始化              |
| 在 `log.cpp` 再写一次默认参数          | 默认实参重复提供              | 默认参数写在公开声明中             |
| `set_min_level()` 后面加 `const` | 成员函数要修改对象状态           | setter 不使用末尾 const      |
| `min_level()` 忘记加 `const`     | 使 const Logger 无法读取等级 | Getter 合理使用 const       |
| `should_log()` 使用 `>`         | 最低等级本身被过滤             | 使用 `>=`                 |
| 以为 const 引用会让 `name_` 也成为引用   | 参数类型与成员类型混淆           | 分清参数 `name` 和成员 `name_` |
| 认为两个 Logger 共享 `min_level_`   | 混淆类与对象                | 每个对象拥有自己的非静态成员          |
| 认为过滤后实参表达式不执行                 | 混淆调用前求值与函数内过滤         | V1 只处理函数内部的输出过滤         |

我特别建议你对前三类问题自己写一段简短代码，观察编译错误，这有助于理解 C++ 的类型系统与 `const` 约束。

## 十八、V1 与后续学习的关系

V1 做完后，Logger 将具有：

```
Logger
│
├── 对象状态
│   ├── name_
│   └── min_level_
│
├── 对外接口
│   ├── Logger(...)
│   ├── set_min_level()
│   ├── min_level()
│   ├── debug()
│   ├── info()
│   ├── warn()
│   └── error()
│
└── 内部实现
    ├── should_log()
    └── log()
```

这时你将真正理解一个 C++ 类如何管理自己的状态，以及这些状态如何影响它的行为。

后续 V2 可以继续引入 `SourceLocation`、`struct` 和宏，让 Logger 自动记录源码位置；V3 再引入可变参数模板，实现直接传递多类型参数的日志接口。

从学习角度来说，V1 最有价值的不是新增了多少代码，而是把几个重要概念串联起来：

构造函数建立初始状态 → 成员变量保存状态 → setter 修改状态 → const getter 读取状态 → 私有函数根据状态决定行为。

这是一条完整、经典的 C++ 类设计链路。
