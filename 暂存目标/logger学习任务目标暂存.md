# C++ Logger 项目制学习路线总纲（V1.0）

## 一、项目背景与学习目标

### 1. 个人背景

我是一名 C++ 初学者，已经学习过部分基础语法，但对现代 C++ 的类与对象、模板、资源管理、智能指针、并发编程和实际工程设计等知识还不够熟悉。

我希望采用**项目驱动学习（Project-Based Learning）**的方式，通过从零开始、逐步实现一个具有实际工程价值的 C++ Logger 日志模块，系统掌握 C++ 的核心知识。

我的目标不只是完成一个 Logger，而是通过不断提出真实需求、升级功能、重构代码，逐渐建立：

- C++ 语言基础与现代 C++ 编程能力。
- 面向对象编程与泛型编程能力。
- 内存管理、资源所有权和对象生命周期意识。
- 多线程、线程同步及并发程序设计能力。
- 软件抽象、接口设计和模块化工程能力。
- CMake、GoogleTest、调试、性能分析与代码质量保障能力。

**核心原则：以 Logger 的真实工程需求驱动 C++ 知识学习，而不是为了使用某种语法刻意增加代码复杂度。**

## 二、项目最终目标

最终实现一个小型但真正具有工程实用价值、可测试、可维护、可复用的现代 C++ Logger。

预期支持：

1. Debug、Info、Warn、Error 日志等级。
2. 独立的 Logger 对象及名称。
3. 运行时日志等级配置。
4. 时间戳、线程 ID、源码位置。
5. 多种 C++ 类型的日志参数。
6. 必要的编译期日志过滤。
7. 控制台日志输出。
8. 文件日志输出。
9. 多输出目标（Sink）。
10. 多线程安全。
11. 日志文件大小轮转。
12. 异步日志队列与后台工作线程。
13. 日志过滤、刷新和关闭机制。
14. 单元测试与并发测试。
15. 性能基准测试与可靠性检查。
16. 可通过 CMake 集成到其他项目。

最终 Logger 的一种可能调用方式：

```cpp
Logger logger(config);

logger.debug("user id=", user_id);
logger.info("application started");
logger.warn("retry count=", retry_count);
logger.error("open file failed: ", filename);
```

以上只是目标 API 示意，具体接口随学习阶段逐步演化，不需要 V0 就实现。

## 三、总体学习路线

将 Logger 分为 11 个版本，从 V0 到 V10。

| 版本 | 核心能力 | 重点 C++ 知识 |
|---|---|---|
| V0 | 最小面向对象 Logger | class、对象、封装、头源分离 |
| V1 | 日志等级与对象配置 | 构造函数、const、引用、对象状态 |
| V2 | 源码位置信息 | struct、宏、预处理器 |
| V3 | 多类型日志参数 | 模板、参数包、折叠表达式 |
| V4 | 线程安全 Logger | thread、mutex、lock_guard、拷贝语义 |
| V5 | 文件日志输出 | fstream、RAII、filesystem、异常 |
| V6 | LogRecord 数据模型 | 数据建模、组合、职责分离 |
| V7 | 多 Sink 日志架构 | 继承、多态、智能指针、移动语义 |
| V8 | 配置与日志文件轮转 | 配置对象、filesystem、边界处理 |
| V9 | 异步 Logger | condition_variable、queue、atomic、线程生命周期 |
| V10 | 工程化与性能优化 | Benchmark、Sanitizer、CMake、测试 |

这些版本是学习路线，而不是已经完成的代码状态。

### V0：最小面向对象 Logger

**工程需求：** 创建一个 Logger 对象，实现 Debug、Info、Warn、Error 四种等级的终端日志输出。

知识点：

- 类与对象：`class`、实例化。
- 成员变量与成员函数。
- `public`、`private` 和封装。
- 构造函数与初始化列表入门。
- `enum class`。
- `namespace`。
- `.h` 与 `.cpp` 分离。
- 函数声明与定义。
- `::` 作用域解析运算符。
- `.` 成员访问运算符。
- 简单的标准输出流。

预期 API：

```cpp
mini_log::Logger logger("app");

logger.debug("debug message");
logger.info("application started");
logger.warn("configuration missing");
logger.error("open file failed");
```

此阶段不引入模板、宏、继承、智能指针或并发。

核心目标是理解：

**类定义一种类型，对象是类的实例，对象具有状态，并通过成员函数表现行为。**

### V1：日志等级与 Logger 对象状态

**工程需求：** 不同 Logger 可以具有不同名称和最低日志输出等级，并支持运行时修改。

新增知识点：

- 成员变量和对象状态。
- 构造函数参数与默认参数。
- `explicit`。
- 成员初始化列表。
- `const` 与 const 成员函数。
- 值传递、引用与 const 引用。
- Getter/Setter。
- 对象生命周期初步。
- 拷贝构造和赋值的初步认识。
- Rule of Zero。

预期能力：

```cpp
Logger app("app", Level::Info);
Logger network("network", Level::Debug);

app.set_min_level(Level::Warn);
```

重点理解不同对象拥有不同状态，以及状态如何影响对象行为。

### V2：源码位置记录

**工程需求：** 发生错误时能够知道日志来自哪个文件、哪一行、哪个函数。

新增知识点：

- `struct` 与 `class` 的区别。
- `__FILE__`。
- `__LINE__`。
- `__func__`。
- `#define`。
- 宏参数与宏展开。
- `__VA_ARGS__`。
- 预处理过程。
- 宏的作用域限制和潜在风险。

引入 `SourceLocation` 数据结构。

目标输出：

```text
[ERROR] [app] main.cpp:35 main | open file failed
```

设计原则：

宏只负责获取源码位置，日志处理仍由普通 C++ 类和函数完成。

### V3：模板与多类型日志参数

**工程需求：** 支持直接记录整数、浮点数、字符串等不同类型，无须手动调用 `std::to_string()`。

新增知识点：

- 函数模板。
- `template<typename T>`。
- 模板实例化。
- 可变参数模板。
- 模板参数包。
- 参数包展开。
- C++17 折叠表达式（Fold Expression）。
- `std::ostringstream`。
- `operator<<`。
- 模板代码通常为何需要在头文件中提供定义。

预期 API：

```cpp
logger.info("user=", name, ", id=", id);
```

重点理解泛型编程解决什么问题，编译器如何根据实参类型实例化模板。

### V4：多线程安全 Logger

**工程需求：** 多个线程可以同时调用同一个 Logger，而不会产生数据竞争，也不会发生日志内容交叉。

新增知识点：

- `std::thread`。
- `std::ref`。
- 共享数据。
- 竞态条件和数据竞争。
- 临界区。
- `std::mutex`。
- `std::lock_guard`。
- RAII 锁管理。
- `mutable`。
- 不可拷贝对象。
- `= delete`。
- 拷贝构造函数和拷贝赋值运算符。
- 锁粒度与死锁基础。

重点实验：

比较未同步、正确同步情况下的多线程日志行为。

要求理解：多线程输出问题不能仅凭肉眼观察日志是否交错来判断，应结合明确的并发正确性测试和工具检查。

### V5：文件日志与 RAII

**工程需求：** Logger 可以把日志写入文件，能够处理文件打开失败、写入失败和对象销毁等情况。

新增知识点：

- `std::ofstream`。
- 文件流状态。
- `std::filesystem`。
- 文件创建与目录管理。
- 对象生命周期。
- 构造与析构。
- RAII。
- 资源所有权。
- Rule of Zero / Rule of Five 的比较。
- 异常与错误处理。
- 异常安全基础。

核心目标：

理解 C++ 如何通过对象生命周期自动管理资源，而非依赖手动释放。

### V6：LogRecord 数据建模

**工程需求：** 一条日志具有时间、等级、名称、消息、源码位置和线程 ID，随着字段增加，原有参数列表和日志函数越来越复杂。

新增知识点：

- `struct` 数据建模。
- 类的组合（Composition）。
- 聚合与数据成员。
- 按值传递和按引用传递。
- `std::chrono`。
- `std::thread::id`。
- 单一职责原则。
- 模块与职责边界。
- 数据和行为的合理组织。

设计 `LogRecord`，将日志信息表达为独立的数据对象。

预期流程：

```text
Logger
   ↓
LogRecord
   ↓
输出处理
```

重点理解：什么时候应该引入新类型，而不是不断增加函数参数。

### V7：Sink 架构、继承与多态

**工程需求：** 同一条日志同时写入控制台、文件，并可以继续扩展其他输出目标。

新增知识点：

- 接口抽象。
- 基类与派生类。
- public inheritance。
- `virtual`。
- 纯虚函数。
- 抽象基类。
- `override`。
- 虚析构函数。
- 运行时多态。
- `std::unique_ptr`。
- `std::make_unique`。
- `std::move`。
- 移动语义。
- `std::vector`。
- 对象所有权与生命周期。

建议建立：

```text
               Logger
                  |
              LogRecord
                  |
               LogSink
              /       \
     ConsoleSink     FileSink
```

实际通过 `LogSink` 接口将日志写入不同目标。

为了单元测试，可增加 `MemorySink`，在内存中收集日志结果。

重点理解：

- 为什么需要接口。
- 为什么此时才引入继承和多态。
- 组合与继承的不同用途。
- 谁拥有 Sink。
- 为什么使用 `unique_ptr`。
- 什么时候需要 `std::move`。

### V8：LoggerConfig 与日志文件轮转

**工程需求：** Logger 的配置越来越多，需要集中管理；日志文件持续增长，需要按照大小进行轮转。

新增知识点：

- 配置对象。
- 默认成员初始化。
- 结构体设计。
- STL 容器与必要的配置表示。
- `std::filesystem::file_size`。
- 文件重命名与删除。
- 边界条件。
- 文件系统错误处理。

预期配置：

```cpp
LoggerConfig config;

config.name = "app";
config.min_level = Level::Info;
config.max_file_size = 10 * 1024 * 1024;
```

目标行为：

```text
app.log
app.log.1
app.log.2
app.log.3
```

重点测试文件大小边界、最大文件数量、文件系统操作失败等情况。

### V9：异步 Logger

**工程需求：** 同步文件写入可能阻塞业务线程，因此引入日志队列和独立工作线程。

新增知识点：

- 生产者消费者模型。
- `std::queue`。
- `std::mutex`。
- `std::condition_variable`。
- `std::unique_lock`。
- `std::thread`。
- `std::atomic`。
- Lambda。
- 移动语义。
- 线程启动与退出。
- `join()`。
- 线程间状态同步。
- 阻塞队列。
- 有界队列与背压。
- 并发对象生命周期。
- 关闭、刷新及异常处理。

预期架构：

```text
业务线程 1 ──┐
             │
业务线程 2 ──┼──> Queue
             │       │
业务线程 3 ──┘       │
                     ↓
                Worker Thread
                     │
                     ↓
                LogSink
```

重点思考：

- 队列满了怎么办？
- 是否丢弃日志？
- 是否阻塞生产者？
- 如何优雅关闭？
- Logger 析构时如何处理剩余日志？
- 异步模式如何保证消息的生命周期？
- 后台线程异常如何处理？
- 如何实现可靠的 `flush()`？

此阶段是高级学习内容，不应提前引入。

### V10：性能、可靠性与工程化

**工程需求：** Logger 已经具备主要功能，接下来关注性能、稳定性、可维护性及复用性。

新增知识点和工具：

- `std::chrono::steady_clock`。
- 性能基准测试。
- 吞吐量、延迟和锁竞争。
- 同步与异步性能比较。
- 编译器优化选项。
- `-Wall`、`-Wextra`、`-Wpedantic`。
- AddressSanitizer。
- UndefinedBehaviorSanitizer。
- ThreadSanitizer。
- GoogleTest。
- CTest。
- CMake target 管理。
- 静态库及必要的安装导出配置。
- API 文档、README 和示例项目。
- 编译、链接与运行期错误排查。

应设计有意义的基准场景，包括：

- 禁止输出的日志调用开销。
- 字符串格式化开销。
- 单线程和多线程。
- ConsoleSink 与 FileSink。
- 同步与异步。
- 不同 flush 策略。
- 不同队列容量及消息大小。

测试中区分日志调用耗时、日志实际落地耗时和程序退出前的总耗时，避免误导性的性能结论。

## 五、贯穿所有阶段的设计原则

1. **需求驱动知识点。** 不为了学习某个关键字而刻意使用它，而是从真实需求中引出相关知识。
2. **一次只引入有限的新概念。** 让每个版本的复杂度可控。
3. **保持可运行状态。** 每个版本都应该能够独立编译、执行和验证。
4. **先理解问题，再学习解决方案。** 尤其是线程安全、资源管理、多态和异步设计。
5. **优先使用现代 C++ 最佳实践。** 例如 RAII、Rule of Zero 和清晰的资源所有权。
6. **不过度设计。** 不提前加入单例、继承框架、复杂模板元编程、工厂模式、无锁队列等。
7. **渐进式重构。** 不要第一天就创建复杂的 `Logger / Sink / Formatter / Record / AsyncLogger` 体系。
8. **测试贯穿始终。** 从早期就建立基础测试，随着功能升级逐步增强测试能力。
9. **保留演化历史。** 建议每个版本建立独立 Git commit 或 milestone，必要时再拆成多个小提交。
10. **区分教学简化与生产要求。** 对于为了教学暂时省略的可靠性措施，应明确说明其局限，后续逐步补齐。

## 六、希望 AI 采用的教学方式

当我指定某个版本时，不希望直接拿到一整份无法理解的完整代码。

希望采用下面的教学流程：

**第 1 步：分析需求**

明确本版本为什么需要升级，上一版本存在哪些实际局限。

**第 2 步：梳理知识点**

列出必须掌握、建议掌握、拓展理解的 C++ 知识。

解释每个知识点为何出现，解决什么问题，与其他概念有什么区别。

**第 3 步：讲解语言原理**

针对新知识点给出简洁、可独立运行的示例，解释语法、语义、对象生命周期和常见误区。

**第 4 步：设计 Logger**

分析类、成员变量、成员函数、接口、状态和对象之间的关系。

解释设计取舍，说明为什么这样设计，为什么不选择某些更复杂的方案。

**第 5 步：分阶段实现**

将版本拆成多个足够小的子任务，每个子任务有明确目标、修改文件、实现提示和预期结果。

尽量让我先自行思考和实现，再提供参考代码或帮助纠错。

**第 6 步：编译与测试**

说明 CMake 修改、编译方法、GoogleTest 测试案例、正常行为和边界条件。

**第 7 步：错误实验**

有针对性地设计常见错误，例如 const 使用错误、对象复制问题、资源生命周期问题和并发问题。

解释错误产生的原因，而不是只给出修复代码。对于可能导致未定义行为的实验，应明确风险，并推荐安全的观察方式。

**第 8 步：代码审查**

审查正确性、可读性、职责划分、C++ 惯用法和工程合理性。

指出当前版本已解决的问题及仍然存在的限制。

**第 9 步：总结与验收**

提供知识点复习、理解检查题、动手练习、可验证的验收标准及下一版本的衔接。

## 七、学习进度管理约定

不同的新聊天可能只关注其中某个版本，因此必须支持从任意阶段继续学习。

每次开始时：

1. 我会明确给出当前希望学习的版本。
2. AI 先检查仓库实际代码，不得假设之前的版本已经完成。
3. 已有实现应作为本次教学的基线。
4. 如果该版本尚未开始，应从对应知识点和需求分析开始。
5. 如果该版本已经部分完成，应围绕未完成内容继续。
6. 先前阶段无需逐个重新讲解，除非存在必要的前置知识缺口。
7. 如果实际工程需要，可以对原有版本划分和实现顺序进行小幅调整，但需要说明原因。
8. 每阶段结束时形成简短的学习进度记录，包含当前 commit、已实现功能、已掌握知识、尚存问题及下一步计划。

完成某个阶段后，应该把实际完成状态写入进度记录，而不能仅因为课程规划中列出了该版本，就默认已经掌握对应知识。
